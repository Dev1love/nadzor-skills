# tech-check-skills

Я Влад Коновалов, 11 лет в разработке, 8 из них руководил своим агентством. Сейчас делаю проекты сам или с минимальной командой, большую часть кода пишут агенты. Здесь скиллы для Claude Code, которыми я проверяю их работу.

Агент быстро пишет код и уверенно отчитывается «готово, тесты проходят». Эти скиллы проверяют, правда ли это: по диффу, запускам и запросам, а не по словам. Общие правила у всех:

- **Свежий взгляд.** Ищет субагент без контекста сессии. Основная сессия проверяет каждую находку по `file:line` и выкидывает ложные. Сессия, которая писала код, сама себя не ревьюит.
- **Доказательство или «подозрение».** Находка без файла и строки, команды или запроса не считается.
- **Ничего не правят без согласия.** Только отчёт. Временные поломки (саботаж в тестах) откатываются, и в отчёте видно, что рабочее дерево чистое.
- **Наружу ничего без спроса.** Запросы только к локальному запуску или стенду, комментарии в трекер только после подтверждения.
- **Спорное решает человек.** Объединять ли похожий код, выносить ли логику в слой: скилл не утверждает сам, а выносит в «решать вам» с доводом за и против.
- **Короткий отчёт.** Вердикт одной строкой, главное в таблице до 7 строк, остальное по строке. Доказательства полностью по запросу.

## Скиллы

| Скилл | Что делает | Когда |
|---|---|---|
| [`verify-claims`](skills/verify-claims/SKILL.md) | Сверяет отчёт агента с диффом и запусками: что заявлено, но не сделано, и что сделано, но не заявлено. Красные флаги: проглоченные ошибки, хардкод под тест, выключенные тесты, изменения вне задачи | Агент сказал «готово» |
| [`dry-kiss-yagni-srp`](skills/dry-kiss-yagni-srp/SKILL.md) | Вариант скилла `dry-kiss-yagni` автора с SRP и DIP: KISS, DRY, YAGNI, SRP, DIP плюс имена и комментарии. Отдельно оценивает баланс: исправление не должно быть сложнее проблемы | Конец задачи, перед коммитом |
| [`test-auditor`](skills/test-auditor/SKILL.md) | Для каждого теста называет баг, который тест поймает. Пустые, дублирующие, мокающие сам себя тесты. Саботаж: сломать код и убедиться, что тест упал | Агент писал или менял тесты |
| [`security-audit`](skills/security-audit/SKILL.md) | Права на сервере, чужие данные по id, подмена полей, вебхуки и платежи, инъекции, сессии, CORS, миграции, зависимости, доступы агента и CI | Трогали права, API, БД, вебхуки; перед релизом |
| [`leak-guard`](skills/leak-guard/SKILL.md) | Периметр: секреты в коде и истории git, ключи во фронтенде, что торчит наружу, что уходит третьим сторонам. Отчёт светофором для не разработчика | Перед каждой выкладкой |
| [`task-trail`](skills/task-trail/SKILL.md) | След задачи: старт задачи, сообщение коммита с номером, запись решения, «почему код такой» через blame, аудит коммитов без задачи | Старт задачи, коммит, PR |

Границы между скиллами проведены специально: `security-audit` разбирает логику, `leak-guard` разбирает то, что утекает и торчит наружу. `test-auditor` оценивает качество тестов, а `verify-claims` проверяет утверждение «тесты проходят».

## Установка

Все скиллы для своего пользователя, одной командой:

```bash
mkdir -p ~/.claude/skills && curl -sL https://github.com/Dev1love/tech-check-skills/archive/refs/heads/main.tar.gz | tar xz --strip-components=2 -C ~/.claude/skills tech-check-skills-main/skills
```

Только в один проект: заменить `~/.claude/skills` на `.claude/skills` в папке проекта.

Или просто попросите своего агента: «установи скиллы из github.com/Dev1love/tech-check-skills».

### Перед установкой проверьте скиллы
Это касается любого чужого скилла, этих тоже. Скилл это инструкция, которую агент выполнит с вашими правами: запустит команды, прочитает файлы. Подделок и скиллов с промпт-инъекциями становится всё больше. Перед установкой попросите модель в отдельном чате проверить `SKILL.md` и все файлы рядом: нет ли скрытых инструкций, обращений к сети, отправки данных, команд, которые что-то удаляют или меняют вне задачи. Для повторяемости ставьте конкретный коммит или тег, а не `main`.

### Codex, Cursor, Gemini CLI и другие агенты
Скиллы написаны в открытом формате [Agent Skills](https://agentskills.io) (`SKILL.md`), его понимают Claude Code, Codex, Cursor, Gemini CLI и другие инструменты. Отличается только папка, куда класть скиллы: например, Codex читает `.agents/skills/`. Точный путь смотрите в документации своего инструмента.

Одна оговорка. Шаг «запусти свежего субагента» в скиллах использует субагентов Claude Code. Где их нет, тот же эффект даёт новая сессия: запускайте скилл в чистом чате, не в том, где писался код. А если инструмент скиллы не понимает вовсе, `SKILL.md` это обычная инструкция, её можно вставить как промпт.

## Как запускать

Слеш-командой или обычной фразой (скилл срабатывает по описанию):

```text
/verify-claims отчёт агента в описании PR #42
/dry-kiss-yagni-srp изменения ветки относительно main
/test-auditor
/security-audit весь проект перед релизом
/leak-guard перед выкладкой, сайт example.com мой, можно проверять
/task-trail начинаем задачу #57
```

```text
проверь, правда ли агент всё сделал
проверь тесты: они что-то ловят?
можно выкладывать? нет ли утечек
почему этот код такой? (выделить строки)
```

По умолчанию скиллы смотрят изменения ветки относительно base (`main`/`master`). Чтобы проверить весь проект, скажите это в запросе.

## Порядок применения

**После каждой задачи** (агент отчитался):
1. `verify-claims`: сделано ли то, что заявлено. Запускать в новой сессии, не в той, что писала код.
2. `dry-kiss-yagni-srp`: не переусложнено ли.
3. `test-auditor`: если агент писал или менял тесты.

**Перед PR:**
4. `security-audit` по изменениям: если трогали авторизацию, права, API, БД, вебхуки, конфиги.
5. `task-trail`: сообщение коммита и PR с номером задачи, решения записаны в задачу.

**Перед релизом:**
6. `security-audit` по всему проекту.
7. `leak-guard`: обязательно, особенно если проект делал не разработчик.

**На старте задачи:** `task-trail`: найти задачу, пересказать, задать вопросы до начала работы.

**Автоматический шлагбаум:** [`ci/`](ci/README.md). GitHub Action на каждый PR: секреты в новых коммитах и тесты. Красное не даёт слить PR, пропущенные тесты дают жёлтое предупреждение.

### Дополнительные слои (у автора, не входят в репозиторий)
- **Codex review:** кросс-агентное ревью другой моделью. Ошибки одной модели вторая модель видит лучше, чем она сама. Скилл от [@polyakovbest](https://github.com/artwist-polyakov/polyakov-claude-skills).
- **Адверсарии:** отдельного скилла нет, это просьба «проверь адверсариями». Агент сам поднимает субагентов под задачу; чаще всего главное две вещи: корректна ли реализация, если смотреть с разных сторон, и соответствует ли она задаче. Остальное по ситуации, иногда явно говорю, на что смотреть.

## Обкатка на своих проектах

[`docs/eval-prompt.md`](docs/eval-prompt.md): промпт для сессии реального проекта. Сессия сама предлагает, какие скиллы, на каких PR и в каких других сессиях проекта применить, прогоняет их в чистом контексте и собирает разметку находок (правда / ложь / спорно / уже знал) и правки к скиллам.

## Демо для показа

[`demos/`](demos/README.md): шесть маленьких проектов без зависимостей, по одному на скилл, с памяткой для сцены и образцом отчёта.

```bash
demos/run.sh test-auditor   # собрать демо и запустить на нём скилл
```

## Проверка на учебном проекте

`examples/` содержит маленький магазин (Node + Express + встроенный `node:sqlite`) с реалистичной историей git: чистый `main` и ветка, где «агент» сделал задачу с типичными ошибками ИИ.

- [`examples/PLANTED.md`](examples/PLANTED.md): что заложено (15 ошибок в коде, 5 в процессе, 8 ловушек, которые выглядят плохо, но правильные).
- [`examples/RESULTS.md`](examples/RESULTS.md): что нашёл каждый скилл, что пропустил, что выдумал.
- [`examples/reports/`](examples/reports/): отчёты скиллов как есть.

Воспроизвести:

```bash
examples/build-demo.sh /tmp/demo          # собрать магазин с историей git
examples/run-skill.sh security-audit /tmp/run-security   # прогнать скилл в чистой сессии
```

`run-skill.sh` кладёт в копию только тестируемый скилл и запускает `claude -p`. `PLANTED.md` в копию не попадает.

В `examples/` лежат **намеренно** «утёкшие» ключи (`pg_live_...`, `whk_...`): они ненастоящие, это часть учебного проекта. `.gitleaks.toml` исключает их из сканирования самого репозитория.
