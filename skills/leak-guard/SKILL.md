# Защита от утечек

## Суть
Смотрим на периметр: что уходит наружу и что видно снаружи. Отчёт для человека, который не пишет код: для каждой находки одна фраза «чем грозит» без жаргона. Главное правило: **каждую находку подтвердить** (файл и строка, команда и вывод). Без подтверждения писать «подозрение», а не «утечка».

**Граница с `security-audit`:** логику прав, вебхуков, инъекций разбирает он. Здесь только то, что утекает или торчит.

## Объём
Весь проект + вся история git (не только текущая версия). Если есть живой адрес сайта: **сначала спросить**, что сайт принадлежит пользователю и какие адреса можно проверять. Без разрешения живой сайт не трогать. Что без живого адреса не проверить, честно пометить «не проверялось».

## Шаги
1. **Секреты в истории.** `gitleaks detect --source . --log-opts="--all"` если установлен; иначе `trufflehog git file://.`; иначе вручную:
   `git log --all -p | grep -nEi '(secret|token|passw|api[_-]?key|private[_-]?key)\s*[:=]'` и `git log --all --diff-filter=D --name-only` (удалённые файлы, особенно `.env*`, `*.pem`, дампы).
   Секрет хоть раз попал в историю: его нужно **перевыпустить**, удаления из файла мало.
2. **Секреты в текущем коде и фронтенде.** Поиск по коду; отдельно всё, что попадает в браузер: `public/`, `static/`, клиентские бандлы, переменные с префиксами `NEXT_PUBLIC_`, `VITE_`, `REACT_APP_`, `EXPO_PUBLIC_`. Секретный ключ платёжки или API в клиентском коде = красное. Публичные ключи (publishable, anon key при включённом RLS) не утечка, но сказать, почему.
3. **Что отдаётся наружу.** Ответы API: какие поля уходят (найти, где формируется ответ: `SELECT *`, отдача целой записи). Хеши паролей, токены, чужие персональные данные = красное. Обработчик ошибок: отдаёт ли стектрейс, SQL, пути. Source maps в продакшен-сборке.
4. **Что торчит.** По коду и конфигам: админки и служебные страницы без входа, отладочные эндпоинты, документация API (swagger) в проде, раздача статики из корня (видна ли `.git`, `.env`, бэкапы), публичные бакеты, открытые порты БД в docker-compose/конфигах. С живым адресом и разрешением: `curl -sI <url>/.git/HEAD`, `<url>/.env`, `<url>/swagger`.
5. **Третьи стороны.** Персональные данные в аналитике, пикселях, логах ошибок (Sentry и т.п.), в запросах к ИИ-сервисам; скрипты с чужих доменов (`<script src=...>`).
6. **Базовая защита.** Учётки и пароли по умолчанию в сидах и конфигах, вход без ограничения попыток, токены в URL, нет HTTPS-редиректа (если видно по конфигу).
7. **Проверка находок.** Каждую открыть по `file:line` или повторить команду. Неподтверждённое в «подозрения». Зависимости ставь только в окружение проекта: его docker-образ, venv или чистая установка по lock-файлу в копии. Не копируй `node_modules`/пакеты из других каталогов и не ставь пакеты на хост. Не получается: «не проверить», а не обход. Если поднимаешь приложение локально: свободный порт, временная база, убедиться, что отвечает именно твой процесс; остановить по своему PID.
8. **Отчёт.**

Ничего не правим и не удаляем из истории сами: переписывание истории и перевыпуск ключей делает пользователь.

## Формат отчёта (для не разработчика)
Статусы текстом, без цветных значков:
- `[КРАСНОЕ]` исправить до выкладки — **только подтверждённое** (секрет найден, ответ получен). Нельзя подтвердить без сервера или сети: `[ЖЁЛТОЕ]` с пометкой «проверить на сервере»;
- `[ЖЁЛТОЕ]` исправить скоро;
- `[ЗЕЛЁНОЕ]` проверено, всё в порядке;
- `[НЕ ПРОВЕРЯЛОСЬ]` чем и почему не проверили.

1. **Итог** в две строки: сколько красных и жёлтых, можно ли выкладывать, что сделать первым.
2. **Таблица для человека:** `статус | что нашли | чем грозит | что сделать` (всё простыми словами, без кода), красное сверху.
3. **Для разработчика:** по строке на находку: `N. file:line или коммит: исправление; как проверить (команда)`.
4. **Проверено, всё в порядке:** одной строкой через запятую. **Не проверялось:** одной строкой, почему.
5. **Не утечки, передать в `security-audit`** (обязательно, «нечего» — тоже ответ): одной строкой.

Короткий отчёт: до ~400 слов, его будет читать не разработчик. Ячейка таблицы до ~15 слов, без вступлений и пересказа методики.

## Частые ошибки
| Ошибка | Как правильно |
|---|---|
| Проверить только текущие файлы | Вся история git, включая удалённые файлы |
| «Удалите ключ из файла» | Перевыпустить ключ: история уже у всех, кто клонировал |
| Стучаться на живой сайт без спроса | Сначала спросить, какие адреса можно |
| Публичный ключ записать в утечку | Объяснить, почему он публичный и при каком условии это ок |
| Жаргон в «чем грозит» и «как исправить» | «Любой, кто откроет сайт, увидит ключ и сможет списывать деньги с вашего счёта»; техника отдельной строкой «для разработчика» |
| Писать «утечка» без проверки | «Подозрение» + что нужно, чтобы проверить |
| Поставить красное «может попасть в образ / на сервер» без проверки | Жёлтое «проверить на сервере» + команда проверки |
| Скопировать `node_modules` из соседнего проекта ради сборки | Ставить зависимости в копии по lock-файлу; нельзя — «не проверялось» |
| Переписать историю git самому | Только рекомендация; делает пользователь |
