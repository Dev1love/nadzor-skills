# След задачи

## Суть
Через полгода никто не помнит контекст чата. Остаются коммиты, PR и задачи. Скилл следит, чтобы из кода можно было дойти до причины: `строка → коммит → задача → решение`. Это процесс, а не аудит кода: ошибок в логике он не ищет.

**Наружу ничего не пишем без подтверждения.** Комментарий в трекер, создание задачи, правка PR: сначала показать текст пользователю, отправить после «да».

## Где задачи
По порядку: GitHub Issues (`gh issue list/view`), другой трекер, если к сессии подключён (Linear, Jira, канбан через MCP), файл задач в репо (`TASKS.md`, `TODO.md`, `docs/tasks/`). Формат ссылки на задачу взять из истории: `git log --oneline -50` (`#123: ...`, `PROJ-123 ...`, `[123] ...`). Формата нет: предложить `#<номер>: <что сделано>`.

## Режимы

### 1. Старт задачи
1. Найди задачу по номеру или описанию.
2. Перескажи в 3–5 строках: что нужно, критерии готовности.
3. Отметь, что неясно, противоречит коду или устарело. Вопросы списком.
4. Задачи нет: предложи создать (заголовок + описание + критерии). Работу не блокируй, если пользователь сказал «делаем без задачи», но отметь это в сообщении коммита.

### 2. Коммит и PR
1. Посмотри `git diff --staged` (или дифф ветки для PR).
2. Сообщение: `<ссылка на задачу>: <что сделано>` в формате проекта; тело: зачем, если не очевидно из задачи. Несколько задач: все ссылки.
3. Изменения в диффе, которые к задаче не относятся: предложи вынести в отдельный коммит.
4. Выдай готовое сообщение. Коммитить только если пользователь попросил.

### 3. Запись решения
После обсуждения, смены подхода или неочевидного технического решения: черновик комментария в задачу.
```
Решение: <что решили, 1–2 строки>
Почему: <причина>
Отбросили: <вариант> (почему), <вариант> (почему)
Где в коде: <file или коммит>
```
«Почему» и «Отбросили» только из обсуждения, задачи или истории. Не знаешь: пиши «не записано», не придумывай отброшенные варианты.
Показать пользователю, отправить после подтверждения.

### 4. Разбор истории («почему так»)
`git blame -L <строки> <file>` → `git show <commit>` → номер задачи из сообщения → задача и её комментарии (`gh issue view <N> --comments`) → PR (`gh pr list --search <commit>`). Ответ со ссылками на каждое звено. Цепочка рвётся (коммит без задачи, задача без решения): так и сказать, где рвётся, и не додумывать причину.

### 5. Аудит следа
По запросу или перед релизом, за период или по ветке (`git log <base>..HEAD`):
- доля коммитов без ссылки на задачу, список таких коммитов;
- коммиты со ссылкой на несуществующую или закрытую задолго до коммита задачу;
- коммиты, где сообщение не совпадает с содержимым («fix tests», а внутри новая фича);
- неочевидные решения в диффе (новая абстракция, смена подхода, отключённая проверка) без записи в задаче;
- задачи в статусе «готово», по которым нет коммитов.
Каждая находка с хешем коммита или номером задачи.

## Вывод
Зависит от режима: резюме задачи с вопросами; готовое сообщение коммита; черновик комментария; ответ «почему» со ссылками; таблица аудита `коммит/задача | что не так | что сделать`.

Короткий отчёт: до ~400 слов. Аудит: одна строка итога (доля коммитов без задачи) + таблица до 10 строк + черновики правок (сообщения коммитов, комментарии в задачи) по одной строке. Проблемы в коде, замеченные попутно, одной строкой «передать» со ссылкой на скилл (`security-audit`, `dry-kiss-yagni`, `test-auditor`), без разбора.

## Частые ошибки
| Ошибка | Как правильно |
|---|---|
| Отправить комментарий в трекер сам | Показать черновик, отправить после «да» |
| Придумать номер задачи | Только существующий; нет задачи: предложить создать |
| Объяснить «почему» из своей головы | Только по цепочке blame → коммит → задача; разрыв назвать разрывом |
| Номер задачи в имени переменной/файла | Только в коммите и PR |
| Блокировать работу без задачи | Предложить, отметить в коммите, не мешать |
