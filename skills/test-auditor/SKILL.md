# Аудит тестов

Зелёный тест ничего не доказывает, если он не упадёт при ошибке в коде. Для каждого теста называем конкретный баг, который он поймает. Не назвали: тест пустой. Самые критичные места проверяем саботажем. Тесты и код не правим, только отчёт.

## Рамки
- Код и тесты не меняем, кроме саботажа с обязательным откатом. Копии и временные файлы только в `mktemp -d`, рекурсивно не удаляем.
- Зависимости только в окружение проекта: его docker, venv или установка по lock-файлу в копии. Не вышло: «не проверить», без обходов.

## Объём
По умолчанию тесты из `git diff <base>...HEAD` (плюс незакоммиченные и новые) и код, который они проверяют. Весь набор, если попросили аудит проекта или диффа нет.

## Шаги
1. **Запуск.** Команда как в CI. Записать: всего, прошло, упало, пропущено. `0 tests`, отфильтрованный запуск или команда не как в CI это находка.
2. **Дифф тестов.** `git diff <base>...HEAD -- <тесты>`: что ослабили, удалили или поменяли вместе с кодом. Отсюда чаще всего берётся «тесты проходят, потому что их подогнали».
3. **Субагент** по шаблону ниже. Каждый вердикт ПУСТОЙ перепроверь сам.
4. **Саботаж** в 1–2 самых критичных местах (деньги, права, чужие данные): чистое дерево, одна поломка в коде, а не в тесте (`>` на `>=`, убрать проверку владельца, вернуть константу), запуск связанных тестов, откат и `git status --short`. Тест не упал: это доказанный пустой тест, важность высокая.

## Промпт субагенту
```
Ты аудитор тестов, на языке пользователя. Код не меняй; тесты запускать можно, временное в mktemp -d.
Тесты: <файлы>. Код: <файлы>. Запуск: <всего / прошло / пропущено>. Дифф тестов: git diff <base>...HEAD -- <тесты>.
Для каждого теста одной фразой: «если в <функция> поменять <что>, тест упадёт». Не можешь назвать: ПУСТОЙ.
Вердикты: ОК; ПУСТОЙ (в том числе проверяет мок или сам себя, ожидание совпадает с захардкоженной константой); ДУБЛЬ (чего); ПОДОЗРИТЕЛЬНЫЙ (ослаблен в этом изменении, skip/only, зависит от времени или порядка, ожидание подогнано под поведение, а не под задачу).
Ещё: непокрытые критичные сценарии, которые реально есть в коде; 1–2 места для саботажа (file:line, какая поломка, какой тест должен упасть).
Каждая находка с file:line. До 500 слов.
```

## Отчёт
До ~400 слов.
1. **Итог** строкой: сколько тестов реально ловят баги; команда, прошло / упало / пропущено.
2. **Проблемные тесты:** `тест (file:line) | вердикт | почему | что сделать`. ОК одной строкой: «остальные N: ОК».
3. **Саботаж:** `поломка | какой тест должен упасть | упал?` и строка «дерево чистое».
4. **Не хватает тестов:** 3–5 строк, только критичное, без требования 100% покрытия.
5. **Передать** ошибки в коде вне тестов другому скиллу: одной строкой, «нечего» тоже ответ.

Числа в итоге считать по таблице.
