# Аудит тестов

## Суть
Зелёные тесты ничего не доказывают, если они не упадут при ошибке в коде. Свежий субагент для каждого теста называет **конкретный баг, который тест поймает**. Не может назвать: тест пустой. Самые критичные места проверяем **саботажем**: вносим поломку, запускаем тест, откатываем. Основная сессия проверяет каждую находку сама. Тесты и код не правим, только отчёт.

## Объём
- **Изменения** (по умолчанию): тестовые файлы из `git diff <base>...HEAD` + незакоммиченные + неотслеживаемые, и код, который они проверяют. Base: ветка, от которой ответвилась задача.
- **Весь набор**: если пользователь попросил аудит проекта или диффа нет.
- Отдельно: `git diff <base>...HEAD -- <тесты>` показывает тесты, которые в этом же изменении **ослабили, удалили или поменяли вместе с кодом**. Это главный источник «тесты проходят, потому что их подогнали».

## Шаги
1. **Объём и запуск.** Определи команду тестов (package.json, Makefile, pyproject, CI-конфиг). Запусти полный набор, запиши: сколько тестов, сколько прошло, сколько пропущено. `0 tests`, отфильтрованный запуск или команда, отличная от CI, это находка.
2. **Субагент** (`general-purpose`) по шаблону ниже.
3. **Проверка.** Каждую находку открыть по `file:line`. Вердикт ПУСТОЙ проверить: правда ли тест не поймает ни одной правдоподобной ошибки.
4. **Саботаж** для 1–2 самых критичных мест (деньги, права доступа, чужие данные):
   - убедись, что рабочее дерево чистое (`git status --short`), иначе сначала `git stash -u` и потом верни;
   - внеси одну минимальную поломку в **код** (не в тест): `>` на `>=`, убрать проверку владельца, вернуть константу;
   - запусти только связанные тесты; запиши, упали или нет;
   - откати: `git checkout -- <файл>` и проверь `git status --short`, что дерево снова как было.
   Если саботаж делаешь в копии проекта: копию держи в `mktemp -d` (её чистит ОС, рекурсивно не удаляй).
   Тест не упал: это доказанный ПУСТОЙ, важность высокая.
5. **Отчёт** пользователю и ждать решения.

## Шаблон промпта субагенту
```
Ты аудитор тестов. На языке пользователя. Код не меняй. Запускать тесты и локальные запросы можно: временные файлы и копии только в `mktemp -d` (системная временная папка, её чистит ОС; рекурсивно не удаляй, `rm -rf` агенту не нужен), свои процессы останавливай по PID. Задача: найти тесты, которые не защищают от реальных ошибок.
Контекст задачи: <2–3 строки>. Тесты: <файлы>. Проверяемый код: <файлы>. Дифф тестов в этом изменении: `git diff <base>...HEAD -- <тесты>`.
Результат запуска: <N тестов, прошло, пропущено>.
Для каждого теста:
1. Назови конкретный баг в коде, который он поймает. Формат: «если в <функция> поменять <что> на <что>, тест упадёт». Абстрактное «проверяет расчёт» не годится.
2. Не можешь назвать: вердикт ПУСТОЙ.
3. Вердикты:
   - ОК: ловит названный баг;
   - ПУСТОЙ: нет проверок, проверки уровня «не undefined / не null / truthy», проверяется только факт вызова мока, мокается сам тестируемый код (тест проверяет мок, а не код), ожидание совпадает с захардкоженной в коде константой и тест не проверяет ни одного другого случая;
   - ДУБЛЬ: ловит ровно то же, что соседний тест (назови какой);
   - ПОДОЗРИТЕЛЬНЫЙ: ослаблен, удалён или изменён в этом же изменении вместе с кодом; skip/only/todo; зависит от времени, порядка запуска, сети; ожидание подогнано под текущее поведение, а не под требование задачи.
4. Непокрытые критичные сценарии: деньги и округление, права доступа, чужие данные (доступ по чужому id), граничные значения, пустые и некорректные входы, повторная обработка. Только то, что реально есть в коде.
5. Для 1–2 самых критичных мест предложи саботаж: файл:строка, какую поломку внести, какой тест должен упасть.
Каждая находка с `file:line` теста. Без этого не пиши её.
ИТОГ (до 500 слов): таблица `тест (file:line) | какой баг ловит | вердикт | что сделать`, сначала ПУСТОЙ и ПОДОЗРИТЕЛЬНЫЙ. Затем 3–5 самых важных недостающих тестов. Затем саботаж.
```

## Формат отчёта пользователю
1. **Итог** одной строкой: N тестов, сколько реально ловят баги; команда запуска, прошло / упало / пропущено.
2. **Проблемные тесты:** таблица `тест (file:line) | вердикт | почему | что сделать`, только не-ОК. ОК одной строкой: «остальные N: ОК».
3. **Саботаж:** `поломка | какой тест должен упасть | упал?`, плюс строка «дерево чистое: `git status --short` пуст».
4. **Не хватает тестов:** 3–5 строк.

Короткий отчёт: до ~400 слов, без вступлений и пересказа методики. Ячейка таблицы до ~15 слов. Больше 7 главных находок: остальные в «Ещё» по одной строке `file:line: что`. Подробные доказательства не вставлять целиком: одной фразой в ячейке, полностью по запросу («покажи доказательство к N»). Итоговые числа (сколько ОК / ПУСТОЙ) считать по таблице. Ошибки в коде вне тестов: одной строкой в «передать» (`security-audit`, `principles-review`).

## Частые ошибки
| Ошибка | Как правильно |
|---|---|
| «Тест проверяет расчёт скидки» | Назвать баг: «если убрать округление, тест упадёт» |
| Поверить, что тест запускается | Запустить самому, посчитать пропущенные |
| Смотреть только текущую версию тестов | Дифф тестов: что ослабили в этом же изменении |
| Саботаж в тесте, а не в коде | Ломаем код; тест должен заметить |
| Забыть откатить саботаж | Откат + `git status --short` в отчёте |
| Править тесты по ходу аудита | Только отчёт; правки после решения пользователя |
| Требовать 100% покрытия | Только критичные сценарии, которые реально есть в коде |
