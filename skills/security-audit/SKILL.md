# Аудит безопасности

## Суть
Ищем то, что ИИ-агенты чаще всего настраивают неправильно: права доступа, вебхуки, подмену полей, конфигурацию. Свежий субагент ищет, основная сессия проверяет каждую находку. Главное правило: **не утверждать «безопасно» и «уязвимо» на словах.** Каждая критичная находка подтверждается проверкой (запрос, тест, вызов), иначе она «подозрение».

**Граница с `leak-guard`:** секреты в коде и истории, ключи во фронтенде, лишние поля в ответах API, стектрейсы наружу, что видно снаружи смотрит `leak-guard`. Здесь секреты только мельком (одна строка в отчёте, если увидел), не разбираем.

## Объём
- **Изменения**: `git diff <base>...HEAD` + незакоммиченное + неотслеживаемые файлы. Но права и вебхуки проверять по всему пути запроса, даже если дифф затронул только часть (мидлвары, роутер, сервис).
- **Проект** (перед релизом, по просьбе): весь код, конфиги, CI, миграции.

## Где проверять «доказательством»
- Можно: локальный запуск, тесты, стенд, который пользователь назвал своим.
- Нельзя без явного разрешения: прод, чужие адреса, отправка реальных платежей и писем. Если проверить нечем, дай команду и ожидаемый результат, пометь «не запускалось».
- Ничего не меняем в коде. Временные данные (тестовые пользователи в локальной БД) создаём только в локальной копии.

## Шаги
1. **Объём и карта.** Список эндпоинтов/обработчиков (роуты, вебхуки, боты, крон), какая авторизация на каждом, откуда берётся текущий пользователь.
2. **Субагент** (`general-purpose`) по шаблону ниже.
3. **Проверка каждой находки** по `file:line`. Ложные выкинуть с причиной.
4. **Доказательство** для каждой критичной и высокой: поднять приложение локально, сделать запрос (`curl` с токеном другого пользователя, вебхук без подписи, PATCH с `role`), записать команду и ответ. Поднимать на свободном порту, на временной базе, и убедиться, что отвечает именно твой процесс (порт может быть занят чужим сервером). Остановить своё приложение по PID, который сам запустил. Временные файлы держать в `mktemp -d` (её чистит ОС, рекурсивно не удалять).
5. **Отчёт** пользователю, ждать решения.

## Шаблон промпта субагенту
```
Ты аудитор безопасности. На языке пользователя. Код не меняй. Запускать тесты и локальные запросы можно: временные файлы и копии только в `mktemp -d` (системная временная папка, её чистит ОС; рекурсивно не удаляй, `rm -rf` агенту не нужен), свои процессы останавливай по PID.
Контекст: <2–3 строки>. Код: <дифф или «весь проект»>. Карта эндпоинтов: <список>.
Секреты в коде и истории, ключи во фронтенде, лишние поля в ответах, стектрейсы смотрит другой аудит: не разбирай, максимум одна строка.
Проверь:
- Права на сервере: проверка только на фронте; эндпоинт не проверяет, что ресурс принадлежит пользователю (чужой заказ/файл/профиль по id); админские действия без проверки роли на сервере; RLS-политики в БД (например Supabase) выключены или `using (true)`.
- Подмена полей (mass assignment): тело запроса целиком уходит в INSERT/UPDATE или ORM (`...req.body`, `Object.assign(user, body)`, имена колонок из ключей тела); можно прислать role, is_admin, balance, owner_id, price.
- Вебхуки и платежи: нет проверки подписи или сравнение подписи не constant-time; нет защиты от повторной обработки одного события; статус оплаты или сумма берутся из запроса клиента, а не подтверждаются у провайдера; ошибка обработки проглатывается и провайдеру уходит 200.
- Ввод: SQL/NoSQL-инъекции (в т.ч. имена колонок и ORDER BY из ввода; whitelist это нормально), XSS (`innerHTML`, `dangerouslySetInnerHTML`, `v-html` с пользовательскими данными), SSRF (сервер ходит по URL из запроса), path traversal (имя файла из запроса в путь), открытые редиректы, загрузка файлов без проверки типа и размера.
- Сессии и токены: JWT без срока жизни, со слабым или захардкоженным секретом, `alg: none`; срок жизни сессии без причины увеличен; токен не инвалидируется при выходе/смене пароля.
- Лимиты: нет ограничения частоты на логине, отправке кодов, дорогих операциях.
- Конфигурация: CORS `*` или отражённый Origin вместе с credentials; отладочный режим в проде.
- Миграции: деструктивные изменения (DROP, изменение типа с потерей данных) без бэкапа и обратной миграции.
- Зависимости: новые пакеты, которых нет в реестре или с названием, похожим на популярный (проверка: `npm view <pkg>`, `pip index versions <pkg>`); лишние новые зависимости.
- Доступы агента и CI: `.claude/settings*.json`, конфиги MCP, CI-секреты и workflow: нет ли доступа к продовым данным и ключам шире, чем нужно; `pull_request_target` с чекаутом чужого кода.
Для каждой находки: важность (критично/высоко/средне), file:line + цитата, сценарий атаки одним предложением, исправление, как доказать (конкретный запрос/команда и ожидаемый результат при уязвимости и после исправления).
Без file:line находку не пиши. Нет уверенности: раздел «подозрения».
ИТОГ (до 600 слов), по убыванию важности.
```

## Формат отчёта пользователю
1. **Вердикт** одной строкой: можно выпускать / нельзя, сколько критичных.
2. **Находки** по убыванию важности, одна строка на находку:
`важность | где (file:line) | атака одним предложением | исправление | доказано: запрос → ответ (или «не запускалось»)`.
3. **Подозрения** (не подтверждено): по строке.
4. **Проверено, проблем нет:** одной строкой через запятую.
5. **Для `leak-guard`:** одной строкой. **Чистота:** одной строкой (стенд остановлен, PID, дерево чистое).

Короткий отчёт: до ~400 слов, без вступлений и пересказа методики. Ячейка таблицы до ~15 слов. Больше 7 главных находок: остальные в «Ещё» по одной строке `file:line: что`. Подробные доказательства не вставлять целиком: одной фразой в ячейке, полностью по запросу («покажи доказательство к N»).

## Частые ошибки
| Ошибка | Как правильно |
|---|---|
| «Эндпоинт защищён» без запроса | Запрос токеном другого пользователя, ответ в отчёте |
| Смотреть только дифф там, где проверка прав в мидлваре | Проследить весь путь запроса |
| Считать whitelist в ORDER BY инъекцией | Проверить, откуда берётся значение |
| Проверять на проде без спроса | Только локально/стенд; прод с явного разрешения |
| `pkill node` после проверки | Остановить только свой процесс по PID |
| Разбирать секреты и стектрейсы подробно | Это `leak-guard`; здесь одна строка |
| Утопить критичное в 30 средних | Критичное первым, средние коротко |
