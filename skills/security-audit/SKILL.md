# Аудит безопасности

Ищем то, что агенты чаще всего настраивают неправильно: права, деньги, подмену полей, конфигурацию. Субагент ищет, основная сессия перепроверяет. «Безопасно» и «уязвимо» на словах не утверждаем: критичное доказываем запросом или тестом, иначе это подозрение.

Граница: секреты, ключи во фронтенде, лишние поля в ответах и стектрейсы разбирает `leak-guard`. Здесь о них одна строка.

## Рамки
- Код не меняем. Доказываем только локально, тестами или на стенде, который пользователь назвал своим. Прод, чужие адреса, реальные платежи и письма только с его явного разрешения. Проверить не на чем: команда, ожидаемый ответ и пометка «не запускалось».
- Приложение на свободном порту и временной базе, проверяем, что отвечает наш процесс, останавливаем по своему PID. Временное в `mktemp -d`, рекурсивно не удаляем.
- Зависимости только в окружение проекта: его docker, venv или установка по lock-файлу в копии. Не вышло: «не проверить», без обходов.

## Шаги
1. **Карта.** Эндпоинты, вебхуки, боты, крон; какая авторизация на каждом, откуда берётся текущий пользователь. Права проверяй по всему пути запроса (мидлвары, роутер, сервис), а не только по диффу.
   **Если проект двигает деньги**, отдельно карта денежных путей: создание через API, коллбэк провайдера, опрос и крон, ручная проводка и админка, возврат, повтор запроса, позднее событие после финального статуса. Проверить каждый путь, а не только входы API.
2. **Субагент** по шаблону ниже.
3. **Перепроверка** каждой находки по `file:line`, ложные выкинуть с причиной.
4. **Доказательство** для критичных и высоких: запрос токеном другого пользователя, вебхук без подписи, запрос с подменённым полем. Команду и ответ в отчёт.

## Промпт субагенту
```
Ты аудитор безопасности, на языке пользователя. Код не меняй; тесты и локальные запросы можно, временное в mktemp -d, зависимости только в окружение проекта.
Контекст: <2–3 строки>. Код: <дифф или весь проект>. Эндпоинты: <карта>. Денежные пути: <список или «нет»>.
Секреты, ключи во фронтенде, лишние поля и стектрейсы не разбирай: это другой аудит.
Сначала самое частое у агентов: права только на фронте и чужие данные по id; подмена полей из тела запроса (role, owner_id, price); вебхуки и платежи (подпись, повторная обработка, статус и сумма от клиента, 200 при сбое). На каждом денежном пути: финальный статус нельзя перезаписать, резерв нельзя снять дважды, валюта и сумма проверяются на входе, сумма коллбэка сверяется с операцией.
Отдельно то, что агенты делают «чтобы заработало»: ослабленные проверки (отключённая проверка SSL, CORS для всех, выключенная проверка прав, пропуск хуков), которые потом не вернули; секреты, оставленные самим агентом в логах, тестовых данных, коммитах; команды и миграции, которые могут уйти с прод-переменными; места, где агент выполняет инструкции из данных (текст задач, README, внешние страницы, чужие скиллы).
Потом остальное по коду: инъекции, XSS, SSRF, пути к файлам, сессии и токены, лимиты частоты, CORS с credentials, миграции без отката, новые пакеты (есть ли в реестре, не подделка ли), лишние доступы агента и CI.
Каждая находка: важность, file:line с цитатой, атака одним предложением, исправление, как доказать. Без file:line не пиши. Не уверен: раздел «подозрения». До 600 слов.
```

## Отчёт
До ~400 слов.
1. **Вердикт** строкой: можно выпускать или нет, сколько критичных.
2. **Находки** по убыванию важности, по строке: `важность | file:line | атака | исправление | доказано: запрос → ответ (или «не запускалось»)`.
3. **Подозрения.**
4. **Проверено, проблем нет:** одной строкой. Денежный путь сюда только после проверки запросом или тестом; «под блокировкой» по коду это ещё подозрение.
5. **Для `leak-guard`** одной строкой. **Чистота:** стенд остановлен, дерево чистое.

Whitelist в `ORDER BY` не инъекция, смотри, откуда приходит значение. Подробные доказательства по запросу.
