# Ревью по принципам: KISS / DRY / YAGNI / SRP / DIP

## Суть
Свежий субагент без контекста сессии смотрит **весь** дифф по пяти принципам и отдельно **имена и комментарии** (вводят ли в заблуждение). Основная сессия **проверяет каждую находку сама** и раскладывает: править сейчас / оставить / решать пользователю. Ничего не правим без согласия пользователя. Сама себя сессия не ревьюит: своё «так задумано» она не видит.

Принципы конфликтуют. SRP и DIP толкают к новым слоям, KISS и YAGNI против них. Исправление, которое добавляет сложности больше, чем пользы на текущем размере проекта, не предлагаем. Пограничные случаи (объединять ли похожий код, выносить ли логику в отдельный слой) скилл сам не решает ни в какую сторону: выносит пользователю с одним доводом за и одним против.

Зона: устройство кода. Безопасность, утечки и качество тестов сюда не входят: если попались, одной строкой в разделе «передать» (`security-audit`, `leak-guard`, `test-auditor`), не в основной таблице.

## Объём
- **Изменения** (по умолчанию): `git diff <base>...HEAD` + `git diff` (незакоммиченное) + `git status --short` (неотслеживаемые файлы тоже в объём). Base: ветка, от которой ответвилась задача (`main`/`master`/указанная пользователем). Во всех затронутых репозиториях и worktree.
- **Проект**: весь код, если пользователь попросил аудит целиком или диффа нет. Тогда в отчёте только находки уровня «высокая» и «средняя».

## Шаги
1. **Объём.** Собери дифф и список новых файлов по правилам выше. Найди документ плана или решений, если есть (`docs/`, `PLAN.md`, `DECISIONS.md`, описание задачи): осознанные решения ревьюер не оспаривает без новой причины.
2. **Субагент** (`general-purpose`, можно в фоне) по шаблону ниже. Подставь пути, base, план, контекст задачи в 2–3 строки.
3. **Проверка.** Каждую находку открыть по `file:line`. Ложную, косметическую или противоречащую записанному решению выкинуть с причиной.
4. **Разложить** в таблицу: `находка → принцип → важность → править сейчас / оставить (почему) / решать пользователю`. К пользователю всё, что меняет поведение или продукт (удаление фичи «за флагом», смена контракта API, перенос в другой модуль или репозиторий), и все пограничные случаи баланса: объединение похожего кода, вынос логики в слой. «Оставить» только когда ответ очевиден (похоже, но меняется по разным причинам). **Бесспорное балансом не взвешивать:** мёртвый код (неиспользуемые методы, импорты, параметры), имена и комментарии, которые врут о сути, — всегда «править сейчас», если правка не меняет поведение. Баланс — только для изменений структуры и поведения (вынос слоя, объединение кода, удаление фичи).
5. **Отчёт** пользователю по формату ниже и ждать выбора. После правок прогнать тесты. Если по ветке идёт внешнее ревью (Codex, ревьюер-человек), отправить правки новым кругом.

## Шаблон промпта субагенту
```
Ты строгий ревьюер с фокусом на KISS, DRY, YAGNI, SRP, DIP. На языке пользователя. Ничего не меняй, только читай.
Задача: <2–3 строки, что и зачем>. План/решения: <путь или «нет»>. Решения оттуда не оспаривай без новой причины.
Код: `git -C <repo> diff <base>...HEAD` + `git -C <repo> diff` + status (новые файлы: <список>).
- KISS: где проще без потери корректности (лишние слои, обёртки, флаги, параметры, конфиги, преждевременная оптимизация, абстракции ради одного вызова).
- DRY: дублирование логики, SQL, констант, валидаций между слоями и файлами. Отдельно ищи копии, которые уже разошлись (в одной округление есть, в другой нет): это баг, а не косметика. Не путай с похожим кодом, который меняется по разным причинам: такое объединять не надо, так и напиши. Вынужденное дублирование отметь как вынужденное.
- YAGNI: сделанное «на будущее»: абстракции, фабрики, интерфейсы, параметры и настройки, которых не требует задача; мёртвый код, неиспользуемые экспорты/параметры/колонки/стили, код за флагом, который никто не включит.
- SRP: файл или функция делает несколько вещей сразу. Бизнес-логика (расчёты, правила, проверки остатков, статусы) в UI, контроллерах, роутах, обработчиках ботов и вебхуков. Сигнал: функцию трудно назвать без «и».
- DIP: внешние зависимости (БД, платёжки, внешние API, почта, текущее время, случайность) импортируются прямо в бизнес-логику, из-за чего её нельзя протестировать без хаков. Не требуй DI-контейнеров: достаточно передать зависимость параметром.
- Баланс: для каждой находки SRP/DIP/DRY оцени, окупится ли исправление на текущем размере проекта. Абстракция оправдана с третьего варианта, не раньше. Явно не окупится: «оставить» и почему. Спорно: «решать пользователю», один довод за, один против. Не выдавай спорное за обязательное. Баланс не применяй к мёртвому коду и врущим именам/комментариям: их править сейчас, если поведение не меняется.
- Имена и комментарии (отдельным блоком):
  · комментарий объясняет ПОЧЕМУ (причину ограничения), а не кто чем не пользуется («страницы мерчанта не просят» → «список уходит в браузер мерчанта как есть, тексты банка ему не показываем»); 1–2 строки, без пересказа кода;
  · номер задачи только в шапке/коммите, не в именах таблиц, вью, файлов, переменных (`task272_src` → по смыслу);
  · слово соответствует действию: копирование ≠ «перенос», если в источнике ничего не убирается; «разовый» только если повтор не нужен;
  · магические числа и позиционные индексы, особенно в тестах (`params[26]`): искать по имени, а не по номеру.
Без косметики ради красоты; имя или комментарий, которые вводят в заблуждение, не косметика.
Безопасность, утечки, качество тестов не твоя зона: максимум одна строка в конце, «передать: ...».
Каждая находка с `file:line` и короткой цитатой кода. Без этого не пиши её.
ИТОГ (до 450 слов): `file:line → принцип → проблема → предложение → важность (высокая/средняя/косметика) → править сейчас / решать пользователю (за/против) / оставить`, по убыванию пользы. В конце вердикт: можно коммитить / сначала поправить. Нет серьёзного: скажи прямо.
```

## Формат отчёта пользователю
1. **Вердикт** одной строкой: можно коммитить / сначала поправить.
2. **Править сейчас:** таблица `# | file:line | принцип | проблема → предложение`, до 7 строк.
3. **Решать вам:** `# | file:line | вопрос | за | против`, по строке.
4. **Оставить:** одной строкой, что похоже на проблему, но не она (и почему).
5. **Передать** (безопасность, утечки, тесты): одной строкой со ссылками на скиллы.

Короткий отчёт: до ~400 слов, без вступлений и пересказа методики. Ячейка таблицы до ~15 слов. Больше 7 главных находок: остальные в «Ещё» по одной строке `file:line: что`. Подробные доказательства не вставлять целиком: одной фразой в ячейке, полностью по запросу («покажи доказательство к N»).

## Частые ошибки
| Ошибка | Как правильно |
|---|---|
| Ревьюить самому, «я же помню код» | Только свежий субагент: свою логику автор не видит |
| Отдать только часть диффа | Все репозитории/worktree + незакоммиченное + неотслеживаемые файлы |
| Принять находки как есть | Каждую сверить с кодом; ложные выкинуть |
| Предложить слой/интерфейс ради SRP или DIP в проекте на 10 файлов | Баланс: если исправление сложнее проблемы, оставить и сказать почему |
| Решить спорный случай самому («обязательно вынести» или молча «оставить») | Вынести пользователю: один довод за, один против |
| Объединить похожий код, который меняется по разным причинам | Это не DRY; отметить «похоже, но не дубль» |
| Пропустить разошедшиеся копии как «косметику DRY» | Расхождение в копиях логики = баг, важность высокая |
| Удалить фичу/флаг по находке YAGNI молча | Это решение пользователя: вынести в отчёт |
| Косметика («вынести константу ради красоты», вкусовые имена) | Не править, если нет реального дубля или риска |
| Пропустить имя/комментарий как «косметику», хотя он врёт о сути | Вводящее в заблуждение править: следующий читатель поверит тексту, а не коду |
| Отправить мёртвый код в «оставить» по правилу баланса | Неиспользуемое без риска удаления — «править сейчас»; баланс только для структуры |
| Переоткрыть решения из плана | Только с новой причиной, явно названной |
| Править после пройденного внешнего ревью и не отправить снова | Изменённый код = новый круг ревью |
